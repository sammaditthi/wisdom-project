# How to Release

One version covers the whole repo — app, static site, research Worker. It
lives in one place, the `version:` line of `pubspec.yaml`:

```yaml
version: 1.0.0+1
#        ^^^^^ ^
#        name  build
```

- **name** `1.0.0` — MAJOR.MINOR.PATCH. What a human sees, and what the git
  tag is named after (`v1.0.0`).
- **build** `+1` — what the App Store and Play Store compare on upload. It
  only ever climbs, and never resets.

Everything else is derived from that line and must not be edited by hand:

| Derived | How |
|---|---|
| `lib/core/version/app_version.gen.dart` | generated by `tools/release.dart` |
| The version row in the settings menu | `AppVersion.display` → `1.0.0 (1)` |
| Git tag `v1.0.0` | `tools/release.dart finish` |
| Android / iOS / Windows bundle version | Flutter reads the pubspec itself |

macOS still hardcodes its bundle version in `project.pbxproj` — deliberately
deferred, see `docs/done/ops/versioning-system.md`.

## The shape of every release

```
bump  →  finish  →  push  →  deploy
```

You never touch the version while building features. It moves only here.

## A bug fix release

Wording, a crash, a layout fix — anything a user would call "a fix".

```bash
dart run tools/release.dart bump patch   # 1.0.0+1 → 1.0.1+2
dart run tools/release.dart finish       # regenerate, commit, tag v1.0.1
git push && git push --tags
./scripts/static_site/deploy.sh --prod   # or whichever product you're shipping
```

## A feature release

Something new that does not break anyone's saved state.

```bash
dart run tools/release.dart bump minor   # 1.0.1+2 → 1.1.0+3   (patch zeroed)
dart run tools/release.dart finish
git push && git push --tags
./scripts/app/web/deploy.sh --prod
```

## A major release

A rewrite, a new reading model, or anything that breaks a user's saved
settings, bookmarks or deep links.

```bash
dart run tools/release.dart bump major   # 1.1.0+3 → 2.0.0+4   (minor and patch zeroed)
dart run tools/release.dart finish
git push && git push --tags
./scripts/app/web/deploy.sh --prod
./scripts/static_site/deploy.sh --prod
./scripts/research_server/deploy.sh --prod
```

## The five commands

```bash
dart run tools/release.dart status
#   version    1.0.0+1  → shows as 1.0.0 (1)
#   tag        v1.0.0 at 489853a
#   commits    3 since v1.0.0
#   generated  up to date

dart run tools/release.dart bump major|minor|patch
#   Rewrites the one pubspec line. Raises that part, and the build by one.
#   minor zeroes patch; major zeroes minor and patch.

dart run tools/release.dart finish
#   Regenerates app_version.gen.dart, commits `chore(release): v1.0.1`
#   (only those two paths — anything else you have staged stays out),
#   and makes the annotated tag. Does NOT push.
#   Refuses unless you are on main with a clean tree apart from those two
#   paths, so it cannot tag a commit the deploy would then reject.

dart run tools/release.dart check
#   Exits 1 if the generated file has drifted from the pubspec; on success
#   its last line is `tag        v1.0.1`. You won't type this; every prod
#   deploy runs it via require_release_commit, which takes the tag name from
#   that line rather than starting Dart a second time. The test suite checks
#   the same drift from its own side, in test/core/version/, without calling
#   this.

dart run tools/release.dart tag
#   Prints `v1.0.1` and nothing else, so a script never has to read the
#   pubspec itself. Nothing calls it today — the deploy guard reads the name
#   out of `check` — but it is the seam for anything wanting the name
#   without the drift gate.
```

## Why a deploy can refuse

Every prod deploy calls `require_release_commit` (`scripts/lib/common.sh`)
before it ships. All four must hold:

| Refusal | Fix |
|---|---|
| not on the release branch | merge first, then release |
| working tree dirty (staged and untracked count) | commit or stash |
| `app_version.gen.dart` drifted from the pubspec | `finish` — never hand-edit it |
| HEAD carries no tag for this version | `bump <part>` then `finish` |

The point is the reverse lookup: a user says "I'm on 1.2.3 and X is broken",
and `git checkout v1.2.3` gives you their exact code.

Two consequences:

- **One version covers every product.** A site-only or Worker-only prod
  deploy still needs a tag. `bump patch` + `finish` is the intended cost.
- **Re-deploying the same commit is free.** The tag is still at HEAD, so the
  guard passes. You only need a new bump once HEAD moves.

Where the guard bites today:

| Script | When |
|---|---|
| `scripts/app/web/deploy.sh` | `--prod`, real runs only |
| `scripts/research_server/deploy.sh` | real runs only |
| `scripts/static_site/deploy.sh` | `--prod`, **including `--dry-run`** |

The android, ios and macos `deploy.sh` are placeholders and exit 3 before any
check. Mobile store releases are gated by `docs/todo/mobile-release/`.

## The first release

Nothing is tagged yet, and `1.0.0` is the version to release, so there is no
bump:

```bash
dart run tools/release.dart finish   # tag v1.0.0; "commit skipped" if nothing changed
git push && git push --tags
```

## Notes

- A store re-upload that needs a fresh build on the *same* name cannot be
  tagged — the tag is `v<name>` with no build number. `bump patch` is the way
  out. Revisit the tag format if that becomes routine.
- Reasoning and the build record: `docs/done/ops/versioning-system.md`.
  Command summary: `tools/README.md`.
