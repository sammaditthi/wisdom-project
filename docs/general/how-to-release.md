# How to Release

One version covers the whole repo — app, static site, research Worker. It
lives in one place, the `version:` line of `pubspec.yaml`:

```yaml
version: 1.0.0+1
#        ^^^^^ ^
#        name  build
```

- **name** `1.0.0` — MAJOR.MINOR.PATCH. What a human sees, and what the git
  tag is named after (`v1.0.0`).
- **build** `+1` — what the App Store and Play Store compare on upload. It
  only ever climbs, and never resets.

Everything else is derived from that line and must not be edited by hand:

| Derived | How |
|---|---|
| `lib/core/version/app_version.gen.dart` | generated by `./scripts/release.sh` |
| The version row in the settings menu | `AppVersion.display` → `1.0.0 (1)` |
| Git tag `v1.0.0` | `./scripts/deploy.sh --prod`, once every test passes |
| Android / iOS / Windows bundle version | Flutter reads the pubspec itself |

macOS still hardcodes its bundle version in `project.pbxproj` — deliberately
deferred, see `docs/done/ops/versioning-system.md`.

## Two commands

```bash
# write the notes under "## Unreleased" in CHANGELOG.md, then:
./scripts/release.sh minor     # raise the version, date the notes, commit
./scripts/deploy.sh --prod     # test, ask, tag, push, deploy every product
```

You never touch the version while building features. It moves only here.
`./scripts/release.sh` on its own says where things stand and what's next.

## Which part

| Part | When | Example |
|---|---|---|
| `patch` | a fix: wording, a crash, a layout | `1.1.0+2 → 1.1.1+3` |
| `minor` | something new that keeps everyone's saved state | `1.1.0+2 → 1.2.0+3` |
| `major` | a rewrite, a new reading model, or anything that breaks saved settings, bookmarks or deep links | `1.1.0+2 → 2.0.0+3` |

The choice is yours. A `feat:` commit can't say whether saved settings break.

## The CHANGELOG entry

`CHANGELOG.md` at the repo root is the release notes. The app's "What's new"
will show it as written, and it pastes into a store's "What's new" as is.
Notes collect under `## Unreleased` at the top — as you go, or all at once from
`git log v<last>..HEAD`:

```markdown
## Unreleased
### New
- Singlish: R types repaya, and c types ච

### Fixed
- Searches with : or ? no longer fail
```

`release.sh minor` turns the first line into `## 1.1.0 - 2026-11-04`, the day
you run it.

- Entries newest first; `## Unreleased` is only ever the top one.
- A plain line straight under the heading is the headline. Write one for
  x.0.0 only.
- `### New`, `### Improved`, `### Fixed`, in that order, each with `- ` notes.
  A note above every group is refused.
- **At most 5 notes a group, and 500 characters an entry** (Google Play's
  limit), counted below the `##` line. Merge similar ones: "UI improvements:
  …" is fine.
- English only, written for a reader, not copied from commit subjects.
- Only what an app reader sees, on any platform. A change for one platform
  says so ("On the web, …"). Website-only changes get no line.

`release.sh` refuses unless `## Unreleased` is the newest entry, with at least
one note and within both limits. `deploy.sh` checks the entry again before it
tags, since notes can be edited after the cut.

## What the two commands do

**`./scripts/release.sh <part>`** — local only, no tag and no push.

1. Refuses unless the tree is clean apart from `CHANGELOG.md`, the last
   version is released (a second bump would skip it), and the notes are
   valid.
2. Raises the pubspec version, dates the `## Unreleased` heading, regenerates
   `app_version.gen.dart`.
3. Commits `chore(release): v1.1.0`, those three files only.

**`./scripts/deploy.sh --prod`**

1. Refuses in seconds: not main, a dirty tree, behind GitHub, a drifted
   version file, no CHANGELOG entry for this version, or this version's tag
   already on another commit.
2. Runs every product's tests (`scripts/test_all.sh`).
3. Asks once.
4. Tags `v1.1.0` and pushes main with it — both or neither (`git push
   --atomic`).
5. Runs each product's `deploy.sh --prod --yes --skip-tests`: research_server,
   then app/web, then static_site. The app calls the Worker and the site links
   into the app, so each goes live after what it depends on. Stops at the
   first failure.

**A red test costs no version.** Nothing is tagged until the tests pass: fix,
commit, run `deploy.sh --prod` again, and the fixed commit gets the tag.

**A failed push or upload:** run it again. The tag is on HEAD, so the tests
are skipped (they passed when it was made), and what already shipped
re-deploys unchanged. The tag covers committed files only: if you rebuilt the
databases since, run `./scripts/app/test.sh` first.

**Picked the wrong part?** While the release commit is HEAD and not pushed:

```bash
git reset HEAD~1     # drop the release commit; the notes stay in the file
git checkout -- pubspec.yaml lib/core/version/app_version.gen.dart
# in CHANGELOG.md, turn "## 1.2.0 - …" back into "## Unreleased"
./scripts/release.sh patch
```

Once `deploy.sh` has pushed the tag, the version stands.

Dev deploys stay each product's own `deploy.sh --dev`. A product's own
`deploy.sh --prod` re-deploys a released commit by itself.

## The conventions this follows

| Convention | Here |
|---|---|
| [Semantic Versioning](https://semver.org) | MAJOR.MINOR.PATCH; you pick the part |
| [Conventional Commits](https://www.conventionalcommits.org) | `feat:` / `fix:` subjects; not used to guess the part |
| [Keep a Changelog](https://keepachangelog.com) | `## Unreleased` dated at release. Groups are New / Improved / Fixed for a store reader, not Added / Changed / Removed for developers |
| Annotated release tags (`git tag -a`) | `v<name>`, made by `deploy.sh` |
| Never move a pushed tag (git docs, "On Re-tagging") | a mistake gets a new version |
| Tests first, then tag (as semantic-release and release-please do) | `deploy.sh` tags only after `test_all.sh` passes |

## Why a deploy can refuse

Every product's prod deploy calls `require_release_commit`
(`scripts/lib/common.sh`) before it ships. All five must hold:

| Refusal | Fix |
|---|---|
| not on the release branch | merge first, then release |
| working tree dirty (staged and untracked count) | commit or stash |
| `app_version.gen.dart` drifted from the pubspec | find the hand edit (`git log -p -- pubspec.yaml lib/core/version/app_version.gen.dart`), undo it, commit |
| the newest CHANGELOG entry is not this version's, or breaks the rules | notes under `## Unreleased` need `release.sh` first |
| HEAD carries no tag for this version | `./scripts/deploy.sh --prod` makes it |

`scripts/deploy.sh` checks the first four itself before its tests, then makes
the fifth.

The point is the reverse lookup: a user says "I'm on 1.2.3 and X is broken",
and `git checkout v1.2.3` gives you their exact code.

Two consequences:

- **One version covers every product.** A site-only change is still
  `release.sh patch` + `deploy.sh --prod`, which re-deploys the rest unchanged.
- **Re-deploying the same commit is free.** The tag is still at HEAD, so the
  guard passes. You only need a new version once HEAD moves past a tag.

Where the guard bites today:

| Script | When |
|---|---|
| `scripts/app/web/deploy.sh` | `--prod`, real runs only |
| `scripts/research_server/deploy.sh` | real runs only |
| `scripts/static_site/deploy.sh` | `--prod`, **including `--dry-run`** |

A product's `--skip-tests` works in prod because of it: only `deploy.sh` makes
the tag, after every test passed.

The android, ios and macos `deploy.sh` are placeholders and exit 3 before any
check. Mobile store releases are gated by `docs/todo/mobile-release/`.

## Underneath

```bash
dart run tools/release.dart status      # what ./scripts/release.sh prints alone
dart run tools/release.dart cut minor   # what ./scripts/release.sh minor runs
dart run tools/release.dart check       # exit 1 if drifted or no valid entry; else `tag  v1.1.0`
```

`check` runs inside every prod deploy, via `require_release_tree`, which reads
the tag name from its `tag` line. The test suite checks the same drift from its
own side, in `test/core/version/`.

## Later: CI

The release commit landing on main, or a "Run workflow" button, starts a job
that runs `./scripts/deploy.sh --prod --yes` — the same command. Before that
works:

- The databases are gitignored, so a checkout has none: the job builds them or
  fetches them from R2.
- The app's full tests need macOS and Chrome: a macOS runner.
- `fetch-depth: 0`, so the checkout has the tags.
- `contents: write`, so the job can push the tag.
- Flutter and Node 22 pinned.

## Notes

- A store re-upload that needs a fresh build on the *same* name cannot be
  tagged — the tag is `v<name>` with no build number. `release.sh patch` is
  the way out. Revisit the tag format if that becomes routine.
- Reasoning and the build record: `docs/done/ops/versioning-system.md`
  (written for the earlier `bump` + `finish` pair). Command summary:
  `tools/README.md`.
